The two-minute read

Build a small prototype lane. Work on access in parallel.

1. Auth is multi-path

82 apps mention OAuth; 62 mention API keys or personal-token paths across API and MCP. These overlap. A private token prototype is not evidence that a distributed OAuth app is approved.

2. “MCP exists” is not enough

Twilio and Mailchimp Marketing expose documentation MCPs. Aircall's partner pages describe Aircall calling external MCPs. Neither proves a general account-action server.

3. Free testing is not launch access

Plaid has a free sandbox but production approval. Grain has free personal access but paid/admin workspace access. DealCloud MCP adds licensing and permissions.

Decision: run a small prototype lane and an access-work lane in parallel. Do not wait for every partner approval before testing self-serve candidates. Do not send unresolved identity or licensing questions to engineering as “ready.”

Readiness routing

Reviewed triage for a scoped prototype, with an explicit rationale per app. An app in “Access work” can still support a private prototype. This is not an exclusive claim that it is unbuildable.

Start with a scoped prototype

  • Attio: free-plan API path; check workspace role and OAuth scope.
  • Linear: key/OAuth developer path; test one read-only workflow.
  • Fathom: API access on every plan; use your own/shared meetings.
  • Mermaid CLI: local adapter rather than a SaaS connector; constrain files and execution.

Readiness shortlist, not an ROI ranking. Customer demand, revenue and engineering estimates were not provided.

What blocks the 30-app access-work lane?

One reviewed primary queue per app, not all possible gates. Plan / tenant / usage entitlement: 12; Distribution / partner / app review: 9; Admin / setup / endpoint permission: 4; Provisioning / identity / security review: 3; Sales / contract: 2. The largest queue is entitlement and tenant access (12/30), followed by distribution/partner review (9/30). Clear these in parallel with engineering prototypes.

Marketing/ads and ecommerce need app-review and production-distribution attention; developer tools and productivity offer more scoped prototype candidates. This is documentation-based triage, not proof that any category is universally free.

Requirements → model → best fit

How the research runs

The requirement is reliable app research at scale. The model is a bounded workflow with review checkpoints. The best fit here is plain Python, versioned JSON, an evidence cache and a static report, not an autonomous framework with hidden decisions.

01 · IntakeExact 100-app manifest
02 · DiscoverOfficial docs and search
03 · FetchPublic HTTPS, cache, hashes
04 · ExtractConservative candidate hints
05 · ReviewSource checks and exception queue
06 · DecideReadiness, next action, report

What actually ran

  • All 100 named apps were researched with official-source reads and additional targeted checks.
  • The Python fetcher attempted 380 unique evidence pages. 362 fetched; 18 failed. Failures stay visible. Of the successful responses, 16 were sparse (under 200 characters), so they need browser/source review. HTTP success is not claim accuracy.
  • The candidate extractor ran across all 100 apps. HTTP-fetch coverage rose from 86 to 99 apps as the run resumed. Sparse-response filtering is saved separately; this is coverage improvement, not accuracy improvement.
  • Validation and offline replay recomputed all counts and the 100-row readiness output.

What still needs an operator

  • Semantic interpretation of product variants, access terms and conflicting sources.
  • Complete the remaining source checks and record sign-off.
  • Credential issuance, OAuth approvals and real endpoint testing, none performed here.
  • Further source review and authorized runtime testing before any production-readiness claim.

Source repository and run instructions

Run without secrets

python research.py replay

# Explicit live source refresh, then a new snapshot:
python research.py refresh
python research.py candidates --output runs/my_first_pass.json

The source package includes README, reviewed JSON, CSV, public-doc cache, fetch outcomes, audit plan and correction history. Confidence is a qualitative source judgment, not a probability. The HTML is standalone. Live refresh does not sign in or call app business APIs. It rechecks the reviewed source manifest; it does not autonomously discover a new app from its name.

Why not force the Composio SDK into this step?

Its strengths are managed per-user auth and tool discovery. Public-document collection does not need account credentials. The brief permits a script/pipeline. A future operational adapter could use Composio after the necessary approvals, but this version does not claim SDK execution.

Trust through visible limits

Real checks. No invented accuracy lift.

5-app source cross-check: 20 fields checked, 16 supported, 0 wrong, 4 unresolved. Grain, Higgsfield, Plaid, Paygent Connect and Mermaid CLI were compared with official docs for auth, access, API/local surface and MCP. All four unresolved fields belong to Paygent Connect: the vendor identity is still not established.

Two access conditions are now clearer: Higgsfield MCP needs a paid subscription; eligible new Plaid teams in the US/Canada have limited real-data Trial access before full Production approval. Original values and refinements are saved in the source package.

This is a selected 5-app check, not 100-app accuracy or a runtime test. It does not complete the assignment's requested manual sample review. The full plan covers 20 apps and 80 fields; a comparable full before/after score is still unavailable. No manual review by the candidate is claimed.

What the baseline taught us

On the fixed 20-app sample, the keyword auth-family baseline exactly matched the reviewed reference for 5, was incomplete or noisy for 13, and remained unresolved for 2. This shows why keyword output cannot be auto-approved.

Diagnostic of one selected sample, not population accuracy. The reference is a reviewed label set, not an independently scored ground-truth dataset. API and MCP auth are checked separately in the row detail.

Owner, contact dates, follow-up due dates and exit evidence are deliberately blank: no outreach or ownership assignment has occurred. Set them when an authorized person starts the work. Role fit is demonstrated through research routing and an explicit operating model, not claimed live approval automation.

Track owner, stage, last evidence date, next action and follow-up date. Suggested policy: one access owner, a dated follow-up after outreach, and an escalation rather than silent abandonment. This case study drafts the playbook; it did not send outreach or obtain approvals.
